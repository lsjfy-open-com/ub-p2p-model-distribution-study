2. 内存管理：Home 所有权与本地副本

基础规范 §9.1～9.3、图 9-1 定义 Home 拥有物理内存、User 通过 UBMD 访问它。UMMU 在 Home 侧完成映射和权限校验；User 侧 Decoder 把地址转换为远端内存描述符。

操作系统参考设计 §4.2.2、§4.3.1、§4.3.2 进一步说明：EXPORT/IMPORT 可把远端资源上线为 NUMA node 或 char device；共享路径通过 mmap 获取虚拟地址后，应用直接使用远端内存。

由此得到两个不同的完成条件：

  • 只导入/映射：访问者可以读取 OM 的远端内存，物理 Home 仍是 OM。不能据此宣布访问者已有本地完整模型副本。
  • 本次分发方案：访问者显式把模型字节读入自己的物理 DRAM，确认完整性和内存可见性后宣布 DRAM 就绪。P2P 的转发端点必须指向这些本地块。

因此 UB 可改善传输路径，池化可扩大可访问的内存资源；单份模型仍只有一个物理 Home 时，其他节点闲置 DDR 通道不会自动分担它的物理供数。要聚合多个物理供数源，需模型实际分片/复制、多 Home 布局，或者已验证的缓存重用、请求合并/复制机制。

缓存可能降低 Home 的物理读取压力。基础规范 §8.2.6 p300 明确描述 Cacheable 访问可降低读取延迟和目标负载。故源网络字节 N×S 与 Home DRAM 控制器实际读取字节不能无条件画等号；仿真 a=1 仍是特定路径假设，应通过内存控制器计数器校准。

3. 协议接口：异步分发与共享映射分别实现

OS 参考设计 §4.2.1～4.2.2 区分 Home 侧的 USVA、KSVA、DMA、EXPORT，以及 User 侧的异步 DMA/URMA 和 Load/Store 访问。§5.3 描述 liburma、Jetty、Segment 和完成记录的工作流程。

本项目优先实现 URMA READ 分块复制到本地注册 DRAM。它不要求每个接收节点把 OM 模型包作为远端 NUMA 内存来使用，也不要求把 OBMM 的 EXPORT/IMPORT 描述符直接当作 URMA Segment 结构。

4. 带宽：lane、端口、节点与内存通道

基础规范 2.1 §3.1.1、图 3-2：端口有独立 TX/RX，每个方向规定 1、2、4 或 8 条 lane 的配置，允许收发宽度不对称及运行中调整有效 lane 数。这里的 lane 是 UB 串行物理通道，不是 CPU DDR 内存通道。

§3.1.2 表 3-1 列出 PHY Mode-1 的 4.0、自定义（含 224.0）和 256.0 Gbit/s，以及 PHY Mode-2 的 2.578125、25.78125、53.125、106.25、212.5 Gbit/s。两端模式与所选速率需要相容，不能把表中所有选项视为任何设备都能同时使用。

例如四个 8-lane、256 Gbit/s/lane 的端口算术和为 1024 GB/s 原始单向能力；它不是已证明的 1000 GB/s 模型载荷能力。基础规范允许自定义速率，本表最高列出值不等于所有产品永远不可超过的统一上限；节点拥有多少端口、哪些端口接到 CPU DRAM 供数路径，仍是产品实现问题。

本规范的这些章节没有为 OM 软件角色规定较低的接口配置，也没有规定目标 CPU 必须具备几条 DDR 通道。现有仿真的 U=200/1000 GB/s 与 DDR5-6400 的 8/12/16 通道仍是公开标注的敏感性参数，不能改称标准保证的设备规格。

5. 功耗机制：可支持定性解释，不能拟合 W→GB/s 曲线

§3.1.1 支持非对称宽度与有效 lane 数调整；§3.2.6 p48～49 描述数据面空闲时可选的 PCS 低功耗机制，通过控制 FEC/扰码相关逻辑的活动减少动态功耗。模式选择与定制速率的限制见 §3.1.2 p20。

这些机制说明“功耗可能随工作状态、有效宽度和实现变化”，但不提供某款整机在 800W/1000W/1200W 下的可持续吞吐、最大并发数或节点数量曲线。空闲时减少 PCS 活动，与满负载强制降宽/降速也不是同一个条件；不能把“更省电”一概解释为更低的满载带宽。

6. 广播/组播与全局缓存：补充候选，不能混入单播基线

§8.6 p310 的多实体协同框架包含融合、集合通信和全局维护，并把广播/组播列为融合操作的例子。规范允许实现者将一次协调调用分解为多个 UB 事务，按照场景和拓扑执行。

这支持继续评估高阶广播/集合分发接口，但没有说明 N 个独立 READ 请求自动变成一次源读取或一次源端发送。若目标软硬件能提供可用的多播/广播分发后端，应列为第三组对照：

  1. 原生 UB 独立单播读取，源网络载荷约 N×S；
  2. 原生 UB＋应用层本地 DRAM 分块转发，固定链源载荷 S；
  3. 可用的 UB 高阶广播/集合实现：按它实际执行的事务图、复制位置和端点流量建模，不能预先套用前两组字节公式。

高阶服务参考设计 §3 描述 uCache 全局 IO 缓存池，§4 描述 MemFabric/SHMEM/MemCache/MemStore；§6、图 6-2 描述 Cache Daemon、跨节点读取和可选存储层。官方确实定义了 UB 上的分布式缓存/存储软件架构，不是只能在 OM 本机保存一份缓存。 它不是保证开箱即有任意配置的硬件缓存设备；要加速本次模型分发，还需确认块的物理布局、复制策略、节点本地 DRAM 落地、API 和兼容性。

MemCache 与 Mooncake Store 的资源预算也不能仅因组件名称不同而忽略；它们都可能占用同一节点 DRAM 容量与访问路径。

7. 管理职责与方案结论

管控运维参考设计 §4.1～4.3 说明 UBM 管理拓扑、CNA/EID、路由、资源、SLA、端口状态和 Telemetry。它是管理组件，不等于本项目应用 OM，也不代表应用 OM 只能使用某种低速端口。当前继续采用用户指定的同构节点假设。

超节点参考架构白皮书 §2 的 TB/s 表述是组件互连架构能力描述；中心推理章节还讨论 KV 的多层次缓存。它们支持研究方向，不构成本项目单 OM DRAM→50/100 个本地 DRAM 副本的实测性能。

本次原文核对后的判断：

  • 纯 UB 独立读取仍是合理首选对照，但按 全体本地 DRAM 就绪 计时，源和目标 DRAM 都纳入预算；
  • UB＋P2P 可通过本地副本分散源端压力，实际收益受转发 DRAM 收发预算、调度窗口、fabric 和在线服务影响；
  • 多 Home 缓存/分片和可用广播/集合后端值得分别评估，避免把 UB 标准中的“平等协同”直接等同于本项目已经实现的 P2P 分发策略；
  • 本次只升级原文证据与方案解释；36 次同构仿真数据仍保持原参数和结果，不追加实机性能主张。
