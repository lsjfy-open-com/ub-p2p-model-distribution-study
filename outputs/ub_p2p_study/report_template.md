# UB＋P2P 模型分发：建模、仿真与分阶段验证报告

**版本：1.0 · 调研日期：2026-09-16 · 研究性质：容量/调度级离散事件仿真**

> 本报告包含实际运行的 Python 仿真，但不包含 Ascend 集群实测、UB 硬件实测或 UB 协议栈仿真。所有未标明来源的数字都是显式实验假设。不能把表中的秒数写成某款 UB 产品的性能承诺。

## 1. 结论与研究范围

建议立项方向是：**一份权威模型制品＋可回收分块缓存＋拓扑感知 P2P 分发＋可替换的 TCP/UB 数据面**。UB 负责节点之间的数据访问和搬运，P2P 负责数据由谁提供、热点如何扩散；二者属于不同维度。

本次实际执行 **{{RUN_COUNT}} 个参数场景**。主场景采用每节点读取 140 GB、100 个空客户端、1 个额外热种子、10 GB/s 单向有效载荷带宽。仿真中的单源耗时 **{{BASE_SINGLE}} 秒**，固定路径分块 P2P 耗时 **{{BASE_P2P}} 秒**。该大幅差异建立在客户端都能同时收发、缓存足够、网络无共享瓶颈、没有竞争业务等条件上，不能外推成实际 UB 加速比。

更稳健的结论有四点：

1. **共享一份模型不会自动消除 N 份读取。** 如果 N 个运行实例各需要完整权重，总接收量仍约为 N×S。
2. **P2P 减少集中源的重复发送，却不减少本实验的总逻辑接收量。** 它通常以更多机器同时供数、更多缓存和更高全网瞬时流量换取更短时间。
3. **源端带宽、拓扑和调度窗口共同决定收益。** 本实验得到强源端/弱 Peer、共享瓶颈和过大发送窗口等反例。
4. **TCP 实测能检验策略，不能证明 UB 的硬件加速。** 后续必须在 UB 机器上完成同一软件、同一工作负载的 2×2 对照。

范围只覆盖“模型数据分发到各节点并可被消费”的阶段。没有模拟权重反序列化、量化转换、图编译、NPU HBM 分配、H2D、推理 warmup 或服务注册；这些另外建立计时边界。用户此前提供的共享聊天链接未能读取正文，本报告不依赖未核实的历史结论。

## 2. 社区调研：可以确认什么

### 2.1 UB 的硬件关联与 DPU 的位置

UB 是包含端点、互联设施及配套软件的体系，DPU 是可能接入其中的设备之一。申请机器需要确认端点/板卡具备目标访问能力，UB 链路和交换拓扑可用，固件、驱动和 OS/SDK 相匹配。现有“Ascend＋鲲鹏”标签不足以确认这些条件。[S1][S2]

对本项目，首个可控工程目标是 **主机 DDR↔DDR 的大块异步传输**。即使某个系统支持跨设备内存访问，也不据此默认任意 Ascend 代际都能完成跨机 HBM 直读，更不默认现有模型加载器能直接使用远端权重执行。

### 2.3 查到的具体规格如何使用

S1 §8 的带宽行写为 **170Gb**，条件为 DPU 智能网卡、单 IODIE、8 KB、32 条流。按带宽表语境理解为 170 Gbit/s 时，相当于 **21.25 GB/s**；原表未把 `/s` 写全，实际采购需厂商确认。时延另一行给出 4 KB、不经过交换机的 20 μs，不能直接当作跨机架每跳延迟。

因此，仿真仅将 21.25 GB/s 放进“源端带宽敏感性”参数点：**它是带条件的数值参照，不是对完整目标硬件的校准。** 没有再对它乘 80%，避免把可能已是测试吞吐的值误当线速重复折损。

主对照的 10 和 40 GB/s 是纯假设，分别可由 100 和 400 Gbit/s 线速乘 80% 得到，但也可代表其他传输栈在实测后得到的有效吞吐。不能把“40 GB/s 档”命名为“UB 实测档”。

## 3. “只保留一份”的四种含义

|层次|可行含义|容量/带宽后果|
|---|---|---|
|逻辑制品|仓库中一个版本、一套哈希与清单|底层持久化仍可冗余，不等于一个物理副本|
|集中热数据|一个源 DDR/共享存储保存完整 S|集中读取可能需要提供 N×S 载荷|
|运行时权重|每个推理实例本地拥有所需 shard|通常产生多份运行数据，UB 不自动消除|
|临时分发缓存|Peer 收到块后转发，完成后回收|可省长期部署包，但本次仿真没有实现提前淘汰|

本次仿真保留所有已收到的块直到结束。100×140 GB 对应客户端最终 **14 TB** 数据，外加种子。它证明的是分发机制，不证明 14 TB 缓存能被消除。若增加本地文件和另一个加载缓冲，峰值容量还会更高。

后续实现可用缓冲池逐块转发和加载，在下游确认收到且本地消费者释放后回收。但何时可回收取决于加载器、重试策略与分块依赖，必须单独测试，不能从本次结果推算小内存窗口足够。

如果每个节点只是多节点模型实例的一部分，应定义需求矩阵 D(i,j)：节点 i 是否需要块 j。总需求 Q=ΣᵢΣⱼD(i,j)×size(j)。只有每节点全量读取时才有 Q=N×S。P2P 应优先按 shard 消费关系构建分发树，避免把不需要的权重广播给所有节点。

## 4. 数学模型、单位与下界

### 4.1 单位

统一使用十进制：1 GB=10⁹ byte；1 GB/s=8 Gbit/s。代码字段 `*_gbps` **均表示 GB/s，不是 Gbit/s**，这是容易误读的命名，读取配置时以本说明为准。MiB 需乘 2²⁰ 转为 byte，不能直接当 MB。

S 表示每个客户端需要接收的模型字节量。140 GB 约等于 70×10⁹ 参数×2 byte 的纯权重，不包括量化元数据、文件封装、镜像、KV cache 和运行时临时内存。这里的“节点”是一个接收与供数实体，可以由一台多 NPU 服务器实现，不代表单张 NPU 必须容纳 140 GB。

### 4.2 集中单源与多种子

```text
T_single ≥ max(N×S / Bs, S / d_min, N×S / F)
T_kseed  ≥ max(N×S / ΣBs_j, S / d_min, N×S / F)
```

Bs 是种子持续可供出的有效载荷带宽，d_min 是最慢客户端的接收能力，F 是对每次逻辑传输计一次的共享容量预算。它不是营销意义上的双向交换总带宽。如果源数据不在内存，Bs 还受实际供数路径限制。

本仿真多种子静态把客户端按 i mod k 分配到种子。节点数不能整除 k 时，在其他资源不限制的条件下，更贴近结果的是：

```text
T_kseed ≈ ceil(N/k) × S / Bs_per_seed + L
```

例如 100 客户端、8 种子、每种子 10 GB/s 时，最忙种子服务 13 个客户端，得到 182 秒，而不是理想均分下界 175 秒。若按块跨种子调度可改善，但本次未实现。

### 4.3 一份初始种子的 P2P 理想下界

```text
T_p2p ≥ max(S / Bs, S / d_min, N×S / (Bs+Σu_i), N×S / F)
```

u_i 是客户端愿意贡献的上传能力。这个下界忽略数据尚未扩散时的因果约束，不能当作可达时间。没有硬件多播、压缩或初始客户端缓存时，总逻辑传输量仍为 N×S；本报告策略使种子发 S、Peer 合计发 (N−1)×S。

### 4.4 额外割集和内存约束

对本策略的任一资源 r，所有占用它的传输量为 V_r，容量为 C_r，则 T≥V_r/C_r。机架出/入方向分别约束；一次跨机架传输在总逻辑流量只计一次，在源机架出口和目标机架入口各占一次预算。

客户端 DDR 采用一个收发共享的有效预算：upload_i + download_i ≤ M_i。内部复制、校验与协议额外访存未逐次建模；需要用实测把物理 DDR 带宽转换为可用的载荷预算。不能把芯片峰值内存带宽直接代入。

### 4.5 流水线策略的可校验闭式解

在相同每跳有效速率 B、固定链条、每发送端一个活跃块、无其他瓶颈，且 S=M×c 可整除时：

```text
T_pipeline = (M + N − 1) × c / B + N × L
           = S/B + (N−1)×c/B + N×L
```

L 是块发送完毕到接收方可发布/转发的延迟。它可并行，不是串行 CPU 校验服务时间。该公式适用于本实现的事件语义，并已用自动化测试对照；不适用于任意拥塞或任意 P2P 调度器。

当 N=100、S=140 GB、c=0.25 GB、B=10 GB/s、L=20 μs：T=14+2.475+0.002=16.477 秒。减小 c 可以降低填充/排空时间，但本模型没有 per-chunk CPU 开销，不能用它确定真实最优分块尺寸。

## 5. 仿真实现及全部默认规格

### 5.1 仿真层次

代码是**流体带宽约束＋分块因果依赖的离散事件模拟器**。没有建立真实连接，没有传输 14 TB 文件，也没有运行推理。它模拟的是多少 GB 数据在什么资源限制下何时完成。

每次事件为一次传输完成或某块可发布。活跃流通过 progressive filling 得到最大最小公平速率：同时受上传、下载、DDR、全局共享预算、源机架出口和目标机架入口限制。每次分配都断言没有越过资源容量。正在传输的块不可提前转发，也不可被第二次送到同一接收节点。

### 5.2 策略

- **single**：一个额外种子，按“块优先、客户端轮转”队列供数。
- **multi**：4/8 个额外且独立供数的预热种子；每客户端绑定一个种子。所有种子放在源机架 0；启用机架限制时，它们共享该机架出口。
- **p2p / fixed**：种子向路径首节点注入全部分块；每块沿包含所有客户端的同一条链依次转发。数据面为节点到节点，控制面可以集中。主实验不需要全去中心化发现协议。
- **p2p / rotating**：对照策略，不同块从不同客户端起步，再沿环绕路径访问每个客户端一次；只执行一个粗粒度策略对照，不宣称最优。

固定链条是易复现的构造性例子，不是生产级 swarm。慢 Peer 可能拖慢大量后继节点；没有失效重试、动态父节点重选和多树容错。

### 6.2 流量和缓存没有消失

{{TRAFFIC_TABLE}}

100 节点主实验中，源端字节从 14,000 GB 降到 140 GB，减少 99%；但全网总逻辑字节都为 14,000 GB。源端峰值在两种策略下仍能达到 10 GB/s，因此“源端总字节减少”也不等于“源端瞬时峰值降低”。P2P 用更多节点同时上传，可能把全局瞬时载荷从 10 GB/s 推高至约 1,000 GB/s。

这正是需要机架感知、全局限速和后台业务预算的原因。不能将“解决源端热点”写成“整个网络带宽不再暴涨”。图中的总流量按逻辑传输计一次，没有包含多级交换逐跳 byte-hop、TCP/UB 头、ACK 或重传。

### 6.4 分块、窗口和强源端

{{CHUNKS_TABLE}}

整模型 140 GB 作为一个块时，所有 Peer 必须等完整模型到达才转发，失去流水线收益。小块极限接近容量下界，但真实小块会增加系统调用、队列操作、校验和调度成本，本仿真未包含这些吞吐损耗。

{{WINDOW_TABLE}}

本实现同一链路上 W 个块分享速率，FIFO 队列导致成批完成。窗口过大会推迟第一批可转发块到达，放大流水线填充时间。真实协议的带宽时延积可能又要求一定队列深度，因此此结果不能用于断言“W=1 总是最佳”。它说明需要分别优化“在途请求深度”和“独立可发布分块”，避免把两者绑死。

{{COUNTER_TABLE}}

这里的 200/2,000 GB/s 是为了构造相对强源端的压力边界，不是已有 UB 产品规格。强源端向多客户端直接并行发送时，P2P 可能没有优势；弱 Peer 或很长的转发链还会拖慢分发。不能只保留最有利的参数场景。

![分块与源带宽敏感性](figures/sensitivity.png)

源带宽图同时显示单源 W=100、P2P W=100 和 P2P W=1，以分离供数能力与发送窗口的影响。过大的 P2P 窗口得到约 261.5 秒，**这是所实现 FIFO 策略的劣化，不是 P2P 技术的不可突破下界**。

## 7. 从分发时间推到服务启动：只能做条件估算

### 7.1 源冷读与预热

设冷模型从存储进入种子内存的持续速率为 R。一次读入 S 的时间为 S/R。

- 先完整预热再分发：T_total=S/R+T_distribution。
- 若能流水重叠：理想下界至少为 max(S/R,T_distribution)，实际还受块供给顺序、排空和共享 DDR 约束。
- 如果每个远程请求都触发磁盘读取，则读取量可能接近 N×S；如果 page cache 命中，物理存储读取可以接近 S，而网络发送仍是 N×S。需要磁盘与网络计数器分别验证。

例如 R=4 GB/s 时，预热 140 GB 需 35 秒。主场景 P2P 完整预热后再分发约 51.477 秒；流水值不能由本次热源实验直接确定。

预置 k 个完整种子要额外 k×S 缓存。若这些种子从同一个权威源逐一获得完整模型，源端预热发送量为 k×S；若第一个种子与权威源共址，则外发可为 (k−1)×S。多种子主表没有计入这个成本，不应拿预热后时间与另一方案从零开始的时间直接比较。

### 7.2 模型加载与服务就绪

设每节点真正加载到加速器的数据为 H，有效装载速率为 B_H，其他初始化/warmup 为 T_init。无重叠情况下：

```text
T_ready = T_distribution + H/B_H + T_init
```

充分重叠时只能给出近似下界 max(T_distribution,H/B_H)+T_init，且还要考虑流水尾部。例：纯假设 H=140 GB、B_H=20 GB/s、T_init=20 秒，附加阶段为 27 秒；分发从 1,400 降至 16.477 秒，则串行 ready 从 1,427 降至 43.477 秒。**这组 ready 数值没有在仿真引擎或实机中执行，仅用于说明 Amdahl 限制。**

如果数据原本已在客户端本地、或初始化/编译占绝大多数时间，再快的网络分发也不一定明显改善业务启动。

## 8. 推荐工程方案

### 8.1 第一阶段：运输层无关的原型

```text
Manifest（版本 / shard / chunk / hash）
                 ↓
拓扑与负载调度器 ── 分块位置目录 / 完成状态 / 限流
                 ↓
节点 Agent：接收 → 完成确认 → 校验 → 发布 → 转发/加载
                 ↓
Transport 接口：TCP backend ｜ 后续 URMA/UB backend
                 ↓
源存储、DDR 缓冲池、可选本地 NVMe、模型加载器
```

数据控制建议：模型内容不可变，版本更新使用新 manifest；逐块正确性确认后再发布；记录 shard 需求；同节点多个 Pod 共享 Agent；发送窗口、接收窗口、校验线程和缓存容量独立配置。

原型先实现本仿真的固定链，复核数据量和流水时间；随后加入多树/多父节点、慢 Peer 绕行和机架感知。不要把仿真中“一个逻辑块完成”直接映射为单个超大 URMA WR，具体传输粒度由设备限制与实测决定。

### 8.2 UB 数据面适配

优先评估两条路线：

1. **直接 URMA 后端**：复用固定注册 Buffer，建立端点，按目标硬件支持的读/写或消息语义搬运；只有完成记录满足可见性要求后，才允许校验和发布。凭据与注册内存必须在在途访问结束后才能回收。
2. **现有 UB 缓存组件后端**：通过 openYuanrong datasystem 或 UBS 相关服务提供块缓存访问；先验证它是否能按需创建多个可供数副本、是否可控制亲和与容量、是否暴露足够指标。全局缓存 API 本身不保证热点已经多副本化。

控制面继续使用 TCP/IP 协调，不妨碍模型数据通过原生 UB 搬运。需要区分“控制面 TCP”和“数据面回退 TCP”。本方案关注后者，不能仅凭服务成功启动就判定 UB 数据面生效。[S1][S3]

### 8.3 对 50～100 节点的调度建议

以机架/UB 互联域为分组优先建立种子；跨域少量注入，域内扩散。按实际拓扑能力决定使用树、环或 mesh，不预设所有 100 节点属于一个无收敛的 UB 域。

分发并发不能无限放开：预留在线推理的网络和 DDR 预算，以数据就绪时限为目标使用最少缓存与必要 Peer 上传。若单源已满足时限，保留简单集中路径；若单源饱和且 Peer/网络有富余，启用 P2P；若只跨域瓶颈明显，可用每域少量热种子。

多源最低数量的容量估算为 k≥ceil(N×S/(T_target×Bs))，同时仍需满足单客户端、共享网络和静态分配不均的条件。例如 N=100、S=140、T_target=30 秒、每种子 10 GB/s，理想均分需要至少 47 个种子；静态整客户端分配时 ceil(100/k)×14≤30，至少需要 50 个种子。这个差异提示块级调度也影响容量规划。

## 10. 验证、可复现性与局限

自动化测试通过 **12 项**：两种公平分配解析例、集中与多种子解析值、P2P 字节守恒、单客户端等价、尾块处理、整文件逐跳、流水闭式解、共享网络约束、内存约束和固定随机种子重复性。每个场景额外断言：不提前转发、不重复投递、总字节正确、源字节正确、资源不超容量、耗时不低于已实现的通用下界。

这些校验提高模型内部可信度，但不构成外部硬件验证。主要局限：

- 无 TCP 拥塞控制、UB credit/拥塞反馈、路由 ECMP、报文重传、MTU、协议头或交换 buffer。
- 无处理器成本、序列化、压缩、哈希吞吐、文件元数据、fsync 和 NPU 实际加载。
- 公平分配是理想资源调度，不承诺真实网络能精确实现；没有利用实机拟合参数。
- 主表客户端全部读完整模型，缓存不淘汰；不适用于稀疏 shard 需求、量化加载或已有本地缓存而不修改模型。
- 拓扑是机架预算抽象，不代表具体 UB Mesh、Dragonfly 网络或采购 BOM。
- 固定路径对慢节点敏感；没有模拟崩溃、故障恢复、限流后台业务和管理面可用性。
- 无统计噪声，不能给出硬件置信区间；确定性仿真的小数只是计算结果，不是测量精度。

复现方式见 README.md。结果保存完整参数、Python/NumPy 环境和运行日志。改变真实机器校准参数后需重跑；复用旧结果时不要只修改报告中的表格。
