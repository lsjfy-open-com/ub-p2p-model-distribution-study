# UB 带宽、功耗、内存共存与分发演进研究

2026-09-20｜公开一手资料核对＋条件计算。没有目标 UB 机器，没有新增实机实验。本文补充此前资源仿真；不将交换设备宣传值当成文件分发速度。

## 1. 结论与方案定位

建议默认采用集中供数、节点 SSD 预置、受控滚动加载，是否启用 P2P 由实测瓶颈决定。内存落地与 SSD 落地是存储选择，集中分发与 P2P 是供数拓扑，二者是独立维度；小集群也可以先落 SSD，大集群也不一定需要 P2P。

不能用“TB/s ÷ 节点数”直接判断本项目速度。必须确认 TB/s 是某端点的单向数据能力、双向之和、多个端口之和，还是整系统指标，并确认 OM 的 SSD/DDR 数据能到达哪些 UB 端口。NPU 互联端口不能默认等价于 OM 文件服务可用端口。

“SSD 不抢占 KV cache 内存”应修正为：SSD 能避免模型部署包长期整包驻留 DRAM；分发和加载期间仍有缓冲、page cache、DDR/CPU/IO 竞争，加载新权重还会占用 HBM。若 Mooncake 同时使用 SSD offload，模型预置会进一步竞争同一磁盘。

## 2. UB 带宽上限与功率：已知和未知

这里 UB 专指 UnifiedBus / 灵衢。Ascend C 文档中的 Unified Buffer 也缩写 UB，它的片上带宽不能用于本研究。

### 2.1 可核对的具体设备例子

华为 Atlas 800T A3 26H1 官方彩页（PDF 第 4 页，零基页码 3）给出 **LingQu 630 V1：48 个 400G 端口，最大输入功耗 1.2 kW**。[S1]

由端口标称速率算术求和：

```text
一个 400 Gbit/s 端口 = 50 GB/s 标称单方向速率
48 × 400 Gbit/s = 19.2 Tbit/s = 2.4 TB/s（单方向端口速率之和）
```

2.4 TB/s 是我们计算的端口速率总和，不是彩页给出的单文件流或 OM 实测吞吐；不是另加接收、发送双计后的可用载荷。某些厂商双向计数得到的数字也不能再当作单向供数能力。

假设 OM 只有一个可用 400G 接入端口，其链路理论上限是 50 GB/s，不是交换机端口总和。实际有效值还受协议、路径、供数与业务保留预算约束。48 个端口也不等于必然接入 48 台服务器：上联、多轨、多平面和冗余都可能占用端口。最简单单端口直连星型需 51 个端点端口才能容纳 1 个 OM＋50 个客户端，单台 48 口设备不够；这是端口计数示例，非该产品组网建议。

同一彩页区分了整套超节点、服务器和交换设备，不能把它们的带宽、节点数和功耗混用。其他代际产品需要重新取得规格；“UB 协议”不存在一个适用于所有设备的单一 GB/s 上限。[S1, S2]

### 2.1 补充复核：端口、节点和 DRAM（2026-09-20）

上一版引用的 48×400G、1.2 kW 来自华为具体交换设备彩页，不是灵衢社区对 UB 通用功率/带宽上限的定义。OM 单 400G 接入也只是条件例子，没有现场证据支持将 OM 默认限制为单口。

在一节点一端口直连的简化拓扑中，48×400G 确实表示最多 48 个这样的节点接入，每个接入口标称 400G；节点实际吞吐仍取决于供数者和其他路径。同一交换机若 OM 也占一个口，则其余为 47 个客户端。多节点各从不同供数端接收可利用多端口并行；多个客户端全部从一个单口 OM 读取，则共同受 OM 那一个出口约束。这两种流量矩阵不能混为一谈。

灵衢社区《灵衢总线技术和软件参考设计》明确描述通过多端口、多路径实现大带宽；openEuler URMA 用户指南 §6.2 明确描述多设备聚合、带宽倍增、故障切换与负载均衡。所以 OM 如果具备受支持的多端口/多设备聚合以及相应内存通路，就可以利用其端点可达的 UB 聚合能力；不能拿单端口上限否定这一点。

对于已预热在 OM DRAM 中的模型，应评估：`有效供数 = min(OM 对外 UB 聚合有效能力, 该 DRAM 区域的实际供数能力, 片内/跨 NUMA 通路, 传输引擎/软件能力, 共享路径剩余容量)`。DRAM 不是 SSD 路径，热分发不能继续使用冷 SSD 读取限制；预热耗时单独计。

DDR 理论带宽按通道和传输率计算：8 个独立 64-bit 通道、6400 MT/s 的假设配置为 409.6 GB/s；16 通道为 819.2 GB/s。这不是目标鲲鹏型号规格，也不是实测远端读取速率。多 DIMM 不必然等于增加独立通道；实际速度还受配置、NUMA、读写混合和现有负载影响。若缓冲/复制额外产生内存流量，实际文件供数速度还低于内存总流量。

如果 OM 到各客户端的真实有效源吞吐分别为 50、200、1000 GB/s，则 50×140 GB 的源端时间下界分别为 140、35、7 秒（接收、SSD、拓扑等均不限制的条件下）。这些仅是条件计算。用户提出的“热模型位于 OM DRAM，集中读取已足够快，无需 P2P”是应优先验证的候选，不应因未经确认的单口假设排除。

补充来源：[社区技术讲义](https://cdn.unifiedbus.com/pdf/2025%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F%E5%B3%B0%E4%BC%9A-%E7%81%B5%E8%A1%A2%E5%88%86%E8%AE%BA%E5%9D%9B-%E7%81%B5%E8%A1%A2%E6%80%BB%E7%BA%BF%E6%8A%80%E6%9C%AF%E5%92%8C%E8%BD%AF%E4%BB%B6%E5%8F%82%E8%80%83%E8%AE%BE%E8%AE%A1.pdf)、[URMA 用户指南 §6.2](https://docs.openeuler.org/zh/docs/24.03_LTS_SP3/unifiedbus/unifiedbus/urma/URMA%20User%20Guide.ch.html)。

### 2.2 功率能否换算带宽和连接数

本轮查到的是最大输入功耗与端口配置，**未找到可用于本项目的不同功率档位→有效带宽→可用连接数的官方测量曲线**。最大输入功耗不是可任意调节的档位，也不是每次满吞吐时的实测功耗。因此不能推导“600 W 对应 24 口”或“功率减半带宽减半”。

一般机制上，端口/模块数量、速率、lane、负载和散热可能影响功耗；电源封顶若触发降频/链路降档，可能降低吞吐，但是否发生及幅度由具体产品决定。端点仍在线而吞吐下降，与主动关端口导致物理连接数减少，是两种现象；还要区别物理连接、逻辑会话和活跃流并发。

现场需要厂家提供并确认：设备/SKU/固件、各端点可用端口数与方向速率、端口到 CPU DDR 的通路、允许功率策略、是否自动降档、拓扑及超售、连接/队列限制。之后在同拓扑同负载下测各受支持档位的有效 GB/s、p99 时延、端口状态、墙上功率、温度、错误与重试。不能修改成设备不支持的功率档位。

能效建议报 `增量能耗/分发字节` 和整个任务能耗，不只报瞬时 W；降功耗但延长任务不必然节能。

## 3. 集中供数是否足够：按时间目标判断

设 N 个空客户端各需 S=140 GB。定义 B 为已扣除在线业务保留量、且综合源供数与共享网络限制后的分发有效总预算；d 为每节点有效接收预算（落 SSD 时还包括持续写入限制）。

```text
T_lower = max(N × S / B, S / d)
N_source_limit = floor(B × T_target / S)
```

N_source_limit 只是同质全量复制条件下的必要容量门槛，不是验证过的可支持集群规模；还须满足接收、拓扑和服务 SLO。已有缓存/shard 场景按实际缺块字节求和，不能直接 NS。

以 T_target=300 秒、每节点 d=4 GB/s 为例（全部是规划假设）：

|分发有效总预算 B|50 节点时间下界|源端预算允许的节点数门槛|
|---|---:|---:|
|4 GB/s|1,750 秒|8|
|10 GB/s|700 秒|21|
|40 GB/s|175 秒|85|
|100 GB/s|70 秒|214|

4 GB/s 可以代表受源 SSD 路径限制的总预算；即使其上接 TB/s 级互连，也不能让冷文件自动以 TB/s 读出。源端 page cache 命中、读一次再 fan-out、逐请求重新读盘的磁盘代价不同，必须实测；网络对客户端总交付仍为 7,000 GB。

假设真能独占 **1 TB/s 单向端到端供数**，50 节点网络下界为 7 秒；若各 SSD 仅能持续 4 GB/s，下界仍至少 35 秒。1 TB/s 在此仅是假设，不是本项目规格。

80 MB/s 如果是单节点旧路径速率，对应 140 GB 用时 1,750 秒；如果是所有节点共享的总速率，则完成 50 份需要 87,500 秒。比较必须统一总带宽/单连接口径。只证明“比 80 MB/s 快”不等于达到初始化时间目标。

`capacity_planning.py` 输出 64 个解析敏感性配置至 `capacity_planning.json`，包含算术校验；它没有拟合功率曲线，也没有模拟 SSD 控制器、page cache 或服务性能，不与此前 122 条离散事件记录混记。

## 4. 分发内存与 Mooncake 的冲突

Mooncake Store 的 `global_segment_size` 表示当前节点/实例贡献给分布式存储池的本地内存，`local_buffer_size` 用于本地传输；同一机器多个实例必须汇总统计。应结合实际版本与进程映射确认，不能把“global”误读为全群仅分配一次。当前源码展示了这两类分配/注册路径。[S3, S4]

规划上至少拆为：

```text
主机 DRAM >= Mooncake 存储区 + 其传输缓冲
           + 推理服务/OS 常驻 + 分发注册缓冲
           + 文件页缓存/脏页 + 模型加载临时峰值 + 安全余量
设备 HBM >= 活跃权重 + 活跃 KV + runtime/workspace + 安全余量
```

这是容量预算，不是可对 RSS 机械求和的统计公式：共享映射、内存池别名和共用注册区须去重。CPU DRAM KV 池与 HBM KV 是不同容量，但权重加载、KV restore 和推理也可能共享 DDR/PCIe/UB 等路径。

示例：512 GiB DRAM，Store 320 GiB、其他服务/OS 96 GiB、安全余量 48 GiB，只剩 48 GiB。140 GB 模型约 130.4 GiB，整包内存缓存不适合；4 条接收流，每条双缓冲 64 MiB，缓冲合计 512 MiB，可以显著降低分发驻留量，但还没有计算 hash、队列、page cache 与加载内存。这些数值是预算示例，不是现场配置。

预分配的 Mooncake 池不一定自动缩小给分发腾内存；注册/锁页内存也不能当作可自由回收的文件缓存。即便容量够用，额外内存带宽和 CPU 消耗仍可能提高 TTFT/TPOT。

## 5. SSD 预置与受控加载

推荐候选路径：

```text
OM 权威模型（控制/目录）→ 供数服务（可与 OM 分离）
  → 有界接收缓冲 → 校验 → 临时 SSD 文件 → 持久化及原子发布
  → 等待加载许可 → 加载所需 shard → HBM → warmup → 服务切换
```

接收块只有在文件完整性与预定持久化条件满足后才宣布模型版本可用。UB 首版仍按 DDR 注册缓冲→SSD 写入设计；没有验证的设备能力时，不假设 UB 直达 SSD 或 SSD 直达 Ascend HBM。

用接收信用/有界队列向上游施加背压，缓冲可从 `并发流数 × 每流缓冲数 × 单缓冲大小` 预算起步。SSD 4 GB/s、每节点链路可送 20 GB/s 时，持续超量接收只会堆积缓冲；应按最慢持续路径限速。

普通 buffered IO 可能使 page cache/dirty pages 增长，所以“文件落盘”不等于不使用内存。应对部署进程设置资源预算并监测内存压力、写回与延迟；可验证 direct IO/对齐和建议性缓存回收的适用性，但不能默认其消除全部内存开销，也不能全局清缓存来保护一个部署任务。

Mooncake 官方 SSD offload 文档表明 KV 可以落到本地文件系统/SSD，因此模型 SSD 预置应优先隔离物理设备或设置可验证的 IO 配额；不同目录不构成磁盘性能隔离。[S5]

- 已有服务：先后台低速预置并校验，随后按服务副本组/TP-PP 组 drain，释放旧实例资源，再加载新模型；保留回滚文件。没有双份 HBM 容量时，不允许仅因 SSD 空间足够就同时启动新旧模型。先确认剩余副本承载能力，不能默认逐物理节点替换对模型并行组安全。
- 无现有服务：仍用有界缓冲写 SSD，再控制加载并发；避免部署包长期占满 DRAM，但模型权重、运行时和 KV 最终仍需内存预算。
- 两种情况：SSD 峰值空间须计新旧版本、临时文件、解压输出、回滚与 KV offload 余量；140 GB 包大小不能代替解压后大小或设备权重峰值。

## 6. 演进路线与触发条件

|阶段|实现|进入下一阶段的证据|
|---|---|---|
|A 集中分发|保留 OM 管理；供数服务→SSD；TCP baseline，未来相同语义切 UB|实测服务 SLO 和初始化时限不满足，定位具体瓶颈|
|B 分发与激活解耦|预置、版本校验、可恢复下载、限流、组级滚动加载|供数仍集中成为热点；先排除 SSD 和加载瓶颈|
|C 多种子/机架缓存|独立供数机器或机架热种子；可从 SSD 提供数据|源/跨架路径不足且 Peer 有空闲读盘与上传预算|
|D 选择性 P2P|按拓扑和业务余量供块，SSD 为持久层、内存只做有界缓冲|与集中/多种子同语义实测确有端到端收益|

B 的资源治理可以在 A 就实施，不必等规模变大。P2P 不能解决所有节点 SSD 写满、共同 fabric 饱和或 HBM 无空间；模型加载是瓶颈时，应改加载调度，而非先增加转发。

## 7. 下一轮实验与当前模拟器差距

现有模拟器的 sink_gbps 只表达持续消费速率，不具备真实落盘、有限缓冲/背压、page cache、已有业务、功率策略和滚动加载模型。不能拿旧时间直接声称“SSD 方案已验证”。

先在当前 Ascend＋鲲鹏 TCP 环境执行：源冷/热缓存 × 空载/现有服务 × 内存/SSD 落地 × 加载并发；每格固定相同数据、校验和完成定义。并发扫描先 1/4/8，再按压力扩大；重复运行报告分布。捕获源/节点有效速率、磁盘读写/延迟、DRAM/HBM 峰值、页缓存/脏页、锁页/注册内存、内存压力、KV 命中率/淘汰/SSD offload、TTFT/TPOT、错误和全体 ready。

功率实验留到 UB 环境：仅用厂商支持的档位，保持同一拓扑/缓存状态和负载，交错运行档位以减小温漂与顺序影响，分别测单连接、满端口聚合、1→N 文件分发及在线业务共存。记录固件、温度和降档状态，建立经验表后才讨论功率与规模映射。

还需用户/现场提供：目标设备 SKU 与组网、OM 访问 UB 的真实通路、支持功率档位；每节点 DRAM/HBM/SSD、Mooncake 版本/实例数/池大小及 SSD offload；模型并行组和 shard；允许的启动时间与在线业务退化阈值。
